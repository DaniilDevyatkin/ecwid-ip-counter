# Unique IPv4 counter (Ecwid / Lightspeed assignment)

Задание: посчитать число **уникальных IPv4-адресов** в текстовом файле, который
может занимать десятки-сотни гигабайт, «используя как можно меньше памяти и времени».
Разрешена только стандартная библиотека Java (21+), нужен рабочий `main()`.

## Подход

Naive-решение из условия (`HashSet<String>`) на полном адресном пространстве 2^32
съедает ~1.4 ГБ heap и по одному объекту на строку. Здесь:

* **битовая карта 2^32 бит = 512 МиБ** — точный ответ по построению, ни одного
  объекта на строку;
* файл читается через **memory-mapped окно 1 ГиБ** (`FileChannel.map`), парсинг
  IPv4 руками по байтам `ByteBuffer` — без `String`, без `split`, без регулярки;
* в том же проходе бесплатно считается **HyperLogLog-оценка** (16k регистров) —
  вторая независимая оценка мощности для sanity check;
* невалидные строки не валят программу, а считаются в `badLines`;
* поддерживаются `\n` и `\r\n`, файл без завершающего перевода строки.

Память при этом фиксированная: 512 МиБ битов + 16 КБ регистров + окно страниц,
независимо от размера файла (кэш окон, которым управляет ОС).

## Запуск

```bash
docker build -t ip-counter .
docker run --rm ip-counter                 # демо: 1M / 4M / 16M строк + сравнение с HashSet
docker run --rm -v "$PWD":/data ip-counter java -Xmx1g -cp /app/classes ipcounter.Main /data/ip.txt
```

Локально:

```bash
mvn -q package
java -Xmx1g -cp target/classes ipcounter.Main /path/to/ip_addresses.txt
```

## Тесты

`mvn test` — 7 тестовых классов-случаев: выборка из условия, CRLF и файл без
перевода строки, пустой файл, мусорные строки, граничные адреса `0.0.0.0`/`255.255.255.255`,
сверка с `HashSet` на случайных данных (1 / 999 / 50 000 строк) и проверка размера
битовой карты.

## Результаты демо-прогона

Сгенерированные файлы: `N` строк, каждая — случайный адрес из пула `N/2`
(то есть примерно половина строк — повторы). Колонки: наше решение против
`HashSet`-бейзлайна на тех же данных.

| строк | файл | точный ответ | HLL | время (наше) | время HashSet |
|------:|-----:|-------------:|----:|-------------:|--------------:|
| 1 M | 11.1 МБ | 432 547 | 431 319 | 0.53 с (20 МБ/с) | 0.32 с |
| 4 M | 47.2 МБ | 1 729 664 | 1 717 422 | 0.23 с (198 МБ/с) | 1.84 с |
| 16 M | 195.8 МБ | 6 917 777 | 6 942 755 | 0.79 с (236 МБ/с) | 9.35 с |

На 16 M строк: **~12x быстрее** naive-решения при фиксированных 512 МиБ вместо
растущего HashSet; JVM с `-Xmx1200m` (1.17 ГБ heap) справляется там, где на
`HashSet<String>` уже нужен heap под ~7 миллионов строк с объектами.

Числа печатает сам `--demo` (таблица заполнена по фактическому выводу прогона,
файл `demo.log` рядом). Настоящий 120 ГБ файл из условия здесь не скачивался
(~20 ГБ zip, на этом хосте 79 ГБ свободного места без риска) — алгоритм от размера
файла не зависит, что и показывает масштабирование 1M → 16M, а тесты покрывают
корректность на границах и на случайных данных.

## Что осталось бы за пределами бюджета

* параллельный проход (разбить файл по границам строк на `Runtime.availableProcessors()`
  кусков, каждый со своей частичной битовой картой, затем OR) — линейно ускоряет,
  но требует ещё 512 МиБ на поток либо `AtomicLongArray`;
* `Fallocate`/`mmap` в файл вместо heap-битовой карты — снимает нагрузку с GC
  окончательно, ценой временного файла;
* проверка на полном 120 ГБ файле из условия (нужен диск ~150 ГБ).
